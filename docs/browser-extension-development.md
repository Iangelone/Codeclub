# Browser extension: development, packaging, and portability

Reviewed October 8, 2026. This document describes the repository implementation and its release process. User instructions and LLM tool contracts are in [Browser Control](browser-control.md); evidence is in [the October 8 audit](tool-audit-2026-10-08.md).

## Source and architecture

| File | Responsibility |
| --- | --- |
| `browser-extension/manifest.json` | Manifest V3 metadata, extension version, permissions, icons, worker, and unpacked public key. |
| `browser-extension/service-worker.js` | Local connection, reconnection, allowed RPC methods, DOM observations, scoped snapshots, native CDP input, and tabs/groups. |
| `browser-extension/icons/` | Runtime icons: 16, 32, 48, and 128 pixels. |
| `electron/browser-extension-config.ts` | Exact accepted extension identities and Edge store/install/removal destinations. |
| `electron/browser-extension-bridge.ts` | Loopback WebSocket server, origin validation, request correlation, timeouts, and cleanup. |
| `electron/external-browser.ts` | Common external-browser interface: companion or direct CDP for DOM work; companion-only tabs/groups. |
| `electron/main.ts` | Native handlers, browser discovery/install actions, and copying bundled unpacked resources. |
| `src/lib/engine/tools.ts` | LLM-facing schemas, executors, and audit metadata. |
| `scripts/package-browser-extension.mjs` | Store ZIP creation without the development key. |

```text
Agent tool -> nativeInvoke/preload -> Electron external-browser control
           -> loopback WebSocket -> extension worker -> browser APIs/CDP
           <- correlated result, new snapshot, or explicit error
```

React displays results; Electron owns native operations. The companion has no AI provider client and no independent model loop. No content scripts, options page, popup, localization files, or build/bundling step currently exist. The manifest description is literal English, so `default_locale` is not currently declared. If localization is added, ship matching `_locales/<locale>/messages.json` files and update the packager's runtime assets; do not add `default_locale` without its resources.

## Connection protocol and trust boundary

Electron binds only `127.0.0.1`, using the first available port from 47832–47842 at `/codeclub-browser`. The worker scans the same ports. A successful connection sends a `hello` browser label and uses ping/pong keep-alives. Browser labels are descriptive; they are not authentication.

Requests contain a correlation `id`, a `method`, and optional `params`. The worker accepts only `listTabs`, `getState`, `action`, and `manageTabs`. Responses contain that ID plus `result`, or an error. Pending bridge calls time out after 15 seconds. Disconnects reject pending calls and the worker detaches its debugger sessions. Debugger attachments also expire after inactivity; snapshot lifetime is one minute.

Manifest V3 can suspend timers. Startup, installation, a toolbar click, and a one-minute alarm wake reconnection. Inter-scan backoff grows to 15 seconds; individual alternate ports are tried with short delays. `ERR_CONNECTION_REFUSED` is expected when no bridge is listening, including between standalone debug runs.

Accepted origins currently use `chrome-extension://` and exactly these identities:

- Unpacked development key: `pomkkenhcjkfjdabdhogladflacafopd`.
- Edge Add-ons: `bomojefgeconjddklieajpeimnjkkbbb`.

The bridge reports `extensionId` from the validated origin. This is an origin allowlist, not cryptographic authentication against an arbitrary native process on the same machine. Do not loosen it to wildcard origins to make a new browser connect. New identities and non-Chromium transports need explicit validation and a matching desktop release.

The worker exposes no arbitrary JavaScript or unrestricted CDP command tool. Native input requires a fresh observed selector, tab visibility, and a usable target. Password values are omitted, but other page text can contain sensitive data; see [privacy](privacy.md). Browser security restrictions on protected pages remain in force. Navigation uses `tabs.update` and does not need to script its source page.

## Development installation

1. Run Codeclub from the repository or install the desktop app.
2. Open the browser's extension manager, enable Developer mode, choose Load unpacked, and select `browser-extension`.
3. Keep its public manifest `key`: it stabilizes the unpacked ID accepted by the bridge. This is not the private `.pem` file generated by CRX packing.
4. Keep the desktop app running for normal use and ask it to list external tabs. Confirm a successful tab-list response and the expected extension ID.
5. Reload the unpacked extension after worker or manifest changes. Restart the desktop app after native/preload changes. Additional permissions may trigger browser prompts.

The desktop installer bundles `browser-extension` through `extraResources`. For non-Edge installation actions, Electron copies it to the app's user-data `browser-extension` directory and opens that copy. Repository edits do not update such a previously copied installation until it is refreshed. Check the exact loaded directory in the browser's extension details. Edge's Install action currently opens the published listing instead.

Do not use Pack extension for the normal development flow. That produces a CRX and potentially a private PEM; neither is the ZIP upload package used below.

## Generate the store upload ZIP

Run from the repository on Windows with Node and PowerShell installed:

```powershell
npm run package:browser-extension
```

The command reads the extension version, not the desktop app version, and writes:

```text
release/codeclub-browser-control-<manifest-version>.zip
```

For the current manifest this is `release/codeclub-browser-control-1.0.2.zip`. Rerunning replaces that generated ZIP. It does not bump versions, sign a CRX, publish, submit certification, or change the unpacked manifest.

The packager stages only the current runtime files, omits `key` from the staged manifest, compresses the contents at archive root, checks the root manifest/key omission/entry count, and prints the output path, version, byte size, file list, and SHA-256. Temporary staging cleanup is restricted to its own generated directory. No new npm dependency or signing credential is required.

Expected layout:

```text
manifest.json
service-worker.js
icons/16.png
icons/32.png
icons/48.png
icons/128.png
```

Do not wrap these files in an extra `browser-extension/` folder inside the ZIP. The README, documentation, node_modules, repository, CRX, PEM, credentials, and desktop installer do not belong in it. If runtime assets are added later, update the packager's explicit manifest-derived file selection before releasing.

**The store manifest must omit `key`.** Edge rejected the first 1.0.2 ZIP because that development-only field was included; the corrected archive and this packager remove it. Keep the source key for unpacked identity stability. Store packaging does not guarantee certification: Partner Center performs its own validation. Microsoft's [publishing guide](https://learn.microsoft.com/en-us/microsoft-edge/extensions/publish/publish-extension) describes uploading the ZIP with its manifest and runtime files.

## Versioning and release checklist

Extension version `browser-extension/manifest.json` and desktop version `package.json` are independent. Change the extension version for an extension release. If the desktop version changes, update package.json and package-lock.json together. Do not change either desktop file's version merely to publish an extension-only update.

1. Review worker changes, manifest permissions, and compatibility with the installed desktop bridge.
2. Update the manifest version to a value higher than the published extension version. The current prepared extension version is 1.0.2; its publication status must be checked in the publisher dashboard.
3. Update [privacy](privacy.md), [listing text and certification notes](listing.md), and the relevant operational guides to match actual behavior.
4. Run the documented verification appropriate to the release, recording browser, profile, source/store installation, and limits. Never equate an isolated fixture with the store package.
5. Generate the ZIP with `npm run package:browser-extension`. Review the printed file list and version; preserve its hash with release records if needed.
6. Upload to the existing store product for an update. Fix validation errors and re-upload; do not create a new product just to replace the package.
7. Provide permission justifications, privacy/support URLs, listing assets, and certification instructions. Submit through the publisher account; building the ZIP is not submission.
8. After publication, verify installation/update from the actual store in the target browser and connection to the supported desktop release. Record the assigned extension ID and acceptance in the bridge.

Generated artifacts belong under ignored `release/`; never commit release packages or signing credentials. The manifest `key` is public and may remain in source. Do not claim a release is published without dashboard evidence.

## Verification commands

```powershell
npm run next:build
npm run electron:compile
npx tsc --noEmit
git diff --check
```

The Next build skips type validation, so TypeScript is a separate check. For explicit extension verification:

```powershell
npm run test:browser-extension
# Optional direct CDP regression:
npm run test:external-browser
```

For the extended isolated Edge suite, set `CODECLUB_DEBUG_ISOLATED_EXECUTABLE` to the browser executable and run `node scripts/debug-live-browser-extended.mjs`. For the connected user-profile suite, unset that variable, close Codeclub completely, keep the main browser visible, and run the same script. It creates three local tabs and a temporary group, then cleans only those resources and restores the previously active tab. These harnesses make no model-provider calls. Never run multiple bridge harnesses concurrently.

The real-profile 22/22 result covers the recorded fixture cases, not arbitrary websites, browser versions, authentication, or all Codeclub tools. The full audit includes intermediate failures and recovery details.

## Portability to other browsers

### Chromium family

The same source uses Chromium APIs (`chrome.debugger`, `tabs`, `tabGroups`, `alarms`) and is intended for Edge, Chrome, Brave, Opera, and Vivaldi. The app detects those Windows browsers and offers installation management. Existing live evidence is strongest for Edge; isolated Chromium also passed. Do not describe all browsers as fully tested.

For each additional browser/store:

1. Load the current source unpacked and confirm its identity, bridge connection, native input, page protection, snapshots, group operations, and wake-up behavior.
2. Check the store's current manifest/API and permission policies. Prepare its listing and privacy disclosures from actual behavior; do not assume Edge certification transfers.
3. Obtain the actual assigned store extension ID. If it differs from accepted identities, add it explicitly to `COMPANION_EXTENSION_IDS` and add an origin regression. Do not assume stripping `key` preserves the unpacked ID.
4. Add the appropriate store/install/removal destinations to native browser management if distributing through that store. The current non-Edge flow is unpacked, not a completed Chrome/Opera store integration.
5. Ship a desktop release accepting that identity before directing users to a package that depends on it. Repeat the real store-install/update checks.

Chrome's [submission preparation](https://developer.chrome.com/docs/webstore/prepare) uses a versioned ZIP. Review Chrome's [key documentation](https://developer.chrome.com/docs/extensions/reference/manifest/key) when managing development versus dashboard identities. The current packager uses a key-free store artifact for Codeclub's workflow; it does not claim identical policy across every store.

### Firefox: a new input adapter is required

Firefox does not implement Chrome's debugger API, so renaming the manifest or adding a browser namespace polyfill will not port this worker. Mozilla documents that incompatibility in [Chrome incompatibilities](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/Chrome_incompatibilities).

A future Firefox port would need an alternative observation/input adapter, Firefox background/lifecycle and permission declarations, and an identity/transport accepted by the desktop bridge. Content scripts could cover some DOM work, but synthetic DOM events do not reproduce all trusted CDP input behavior. Tab/group API support must be checked independently. Preserve the external tool contract where semantics match and report unsupported operations explicitly. Firefox support is not implemented by the current ZIP.

### Safari: extension conversion does not port the desktop host

Apple provides a [Safari Web Extension packaging workflow](https://developer.apple.com/documentation/safariservices/packaging-a-web-extension-for-safari). That workflow does not demonstrate compatibility with this worker's debugger/input transport. A future port needs supported Safari APIs, packaging/signing, identity validation, lifecycle/reconnection work, and equivalent input semantics.

Codeclub currently targets Windows. Safari distribution also needs a supported local desktop host on Apple's platform or a separately designed transport. Neither a Safari worker adapter nor a macOS/iOS Codeclub host is supplied here. Mobile browsers likewise cannot reach a Windows computer through their own `127.0.0.1`; remote-device connectivity would be a separate authenticated design, not a change of port number.

### What to keep shared

Retain the tool names, discovered identities, tab-scoped snapshot rules, explicit errors, result verification, and privacy boundaries where possible. Introduce browser-specific adapters only when a real port requires them. No generic cross-browser framework or silent fallback was added in this work.
