# Revisión de idiomas y diseño

Revisión del 13 de octubre de 2026, sobre el código posterior a b9e71b5. Se inspeccionaron catálogo, hooks, eventos, ventanas, consumidores y configuración. Se ejecutaron consultas de paridad y una reproducción aislada del default de Android, con IPC simulado. No se migraron dependencias ni se cambió código funcional; tampoco se ejecutó una traducción con servicios externos.

## La idea que conviene adoptar

Usar inglés como idioma fuente y separar los textos de la lógica es una buena dirección para este proyecto. Eso significa escribir un mensaje una vez, darle una clave estable y generar/mantener sus versiones en los idiomas soportados. El idioma fuente no obliga a cambiar al inglés la preferencia de un usuario que ya eligió español.

Una biblioteca de internacionalización resuelve qué mensaje mostrar, sus variables y sus plurales. No inventa por sí sola la traducción de un texto nuevo: utiliza recursos que le proporcionamos. Eso también son diccionarios o catálogos, aunque estén mejor organizados. i18next documenta tanto los [recursos y fallbacks](https://www.i18next.com/overview/configuration-options) como la [separación por namespaces](https://react.i18next.com/guides/multiple-translation-files).

Para generar traducciones automáticamente hace falta otra pieza: un traductor, una plataforma de localización o un modelo de IA. Se puede conectar al flujo de desarrollo, guardar resultados y revisar los mensajes importantes antes de empaquetar. La documentación de react-i18next describe [integraciones de gestión y traducción automática](https://react.i18next.com/guides/multiple-translation-files#manage-your-translations-with-a-management-gui); eso es adicional al runtime de la biblioteca.

## Problemas encontrados, por prioridad

### 1. Default distinto en la UI y en Android

La UI arranca en español cuando todavía no existe una preferencia: [i18n.ts](../src/lib/i18n.ts), función useAppLanguage, línea 60. En cambio, androidUnlock usa inglés cuando el valor guardado no es exactamente es: [android-tools.ts](../src/lib/engine/android-tools.ts), línea 27.

La reproducción llamó al ejecutor real de androidUnlock con un bridge simulado. Sin preferencia produjo `Unlock Android`; con es produjo `Desbloquear Android`; con en volvió a inglés. No se contactó ni desbloqueó ningún teléfono. En una instalación nueva puede aparecer un diálogo nativo en otro idioma aunque la app esté en español.

**Corrección:** una sola función para resolver idioma, incluyendo fallback y validación. La UI y las herramientas nativas deben consumir el mismo resultado. Elegir inglés como fuente de traducciones no soluciona este desacuerdo si seguimos decidiendo el idioma por separado.

### 2. El idioma tiene varias fuentes de estado

useAppLanguage crea estado y listeners por consumidor. ChatInterface mantiene además su propio useState y otro listener del mismo evento: [ChatInterface.tsx](../src/components/ChatInterface.tsx), líneas 94 y 234. La sincronización por storage vive en [page.tsx](../src/app/page.tsx), línea 59; el widget también refresca el idioma al mostrarse en [FloatingChat.tsx](../src/components/FloatingChat.tsx), línea 66.

El relevamiento encontró 28 invocaciones de useAppLanguage, además de su definición. Cada montaje comienza con es y luego lee la preferencia persistida; varios consumidores también escriben html.lang. Si hay inglés guardado, los efectos pueden aplicar brevemente el default español antes de resolverlo. Este último efecto se deduce del orden del código; no se midió su duración visual.

**Corrección:** un servicio de locale por renderer, un provider para React y una única integración de persistencia/eventos entre ventanas. Centralizar html.lang y conservar una adaptación temporal de codeclub:language-change mientras se migran consumidores.

### 3. Los mensajes siguen mezclados con componentes y no se exige paridad

El catálogo compartido tiene 29 grupos bilingües y 530 claves del lado español, en un archivo de aproximadamente 43 KB. El relevamiento encontró 154 comparaciones explícitas de language con es/en dentro de src; son ramas de idioma, no 154 traducciones faltantes. ChatInterface concentra 46, WorkspaceLayout 43 y ProjectPanelView 20.

[ChatActivity.tsx](../src/components/ChatActivity.tsx), línea 37, crea otro catálogo de etiquetas de herramientas dentro de una función. Agregar un idioma implica revisar componentes, helpers, errores y mensajes nativos; no alcanza con ampliar i18n.ts. Ya se usan algunas APIs Intl, por lo que no todo el formateo está hecho a mano.

La comparación de claves detectó que rightSidebarTranslations no tiene selectedElement ni closeTerminal en inglés. No encontré consumidores directos de esas propiedades, así que esto demuestra falta de paridad y control, no un texto visible vacío confirmado. El tipado actual sí ayuda a comprobar propiedades usadas, pero no obliga a que todos los catálogos tengan las mismas claves.

**Corrección:** recursos por área, claves tipadas, variables/plurales gestionados por el runtime y un check en CI que compare idiomas, placeholders y mensajes requeridos. No confiar en que instalar una dependencia detecte automáticamente todo el texto suelto.

## Qué biblioteca elegiría

| Alternativa | Encaje en Codeclub | Trabajo que sigue siendo nuestro |
| --- | --- | --- |
| i18next + react-i18next | Mi elección inicial para el renderer de escritorio: una instancia accesible desde React y helpers, recursos agrupados y una API para cambiar idioma. La recomendación se basa en que Electron ejecuta una app exportada y el locale depende de preferencias locales, no de una petición HTTP. | Persistencia, sincronización de ventanas, carga local de recursos y migración del texto disperso. |
| next-intl / use-intl | Alternativa válida con mensajes ICU y formateo; especialmente si el área web gana protagonismo. next-intl también muestra una variante React mediante use-intl, por lo que no requiere necesariamente rutas por idioma. | Decidir correctamente provider/locale en el renderer y evitar copiar una configuración de cookies/server que no corresponde al desktop estático. |

Las características están documentadas en [react-i18next](https://react.i18next.com/latest/usetranslation-hook), [tipado de i18next](https://www.i18next.com/overview/typescript), [plurales](https://www.i18next.com/translation-function/plurals), [next-intl](https://next-intl.dev/) y sus [ejemplos React](https://next-intl.dev/examples). La elección es una propuesta de arquitectura para este repositorio, no un benchmark de rendimiento ni una prueba de compatibilidad ya ejecutada.

## Inglés fuente y traducciones automáticas, sin trabajo repetido en cada componente

El flujo propuesto es:

    mensaje fuente en inglés + clave estable
      -> detectar mensajes nuevos o modificados
      -> generar traducción a español con traductor/IA
      -> validar claves, variables y plurales
      -> revisar contexto y mensajes importantes
      -> guardar catálogos versionados
      -> empaquetar recursos locales
      -> la biblioteca elige el mensaje según la preferencia del usuario

El paso de traducción debe ejecutarse explícitamente al preparar cambios; no esconder llamadas pagas dentro de cada build o de la interfaz. Sólo necesita textos públicos de la UI y su contexto, no conversaciones, claves ni archivos de proyectos del usuario. Una compilación reproducible puede utilizar catálogos ya generados sin necesitar ese servicio.

Así evitamos repetir ternarios y traducir manualmente cada frase en componentes. Seguimos escribiendo los textos fuente y conservando archivos de traducción: eso permite funcionar sin red, revisar cambios, corregir matices y mantener iguales los mensajes entre ejecuciones. Para etiquetas ambiguas y mensajes de permisos/PIN/errores, una traducción automática debe pasar revisión de contexto.

## Lo que esto dice del diseño general

La separación React/Electron es una buena base. Sin embargo, mover funciones a archivos nuevos no termina la separación de responsabilidades: ChatInterface todavía tiene 2.915 líneas y WorkspaceLayout 2.053. El idioma duplicado es un ejemplo de decisiones de aplicación repartidas entre vistas.

El siguiente refactor debería extraer servicios y contratos comunes, no sumar frameworks por nombre. Para idiomas, empezaría por default/estado único, después migraría una superficie con sus tests —por ejemplo Topbar y el panel de archivos—, y luego las restantes. La automatización de traducción viene después de establecer claves y catálogo fuente estables. Las pruebas deben cubrir idioma guardado, cambios entre ventanas, montaje de componentes nuevos, diálogos nativos y formatos/plurales.
